# RMX5200 (AE084) ADFR DTBO injection — 2026-09-26

## 结论先行

把同机另一块面板 AC180 的 ADFR 块注入到 AE084 dvt02 的 WQHD timing 节点后，
内核 **确实** 解析并启用了 AE084 的 ADFR：

| 指标 | 注入前 | 注入后 |
|---|---|---|
| `/sys/kernel/oplus_display/adfr_config` | `0x0`（"adfr is not supported"） | `0xe51` |
| `oplus_adfr_parse_dtsi_config` WQHD120 | 无 mapping table | `[120,60,30,20,10,1]` count=6 |
| `oplus_adfr_parse_dtsi_config` WQHD60 | 无 mapping table | `[60,40,30,20,10,1]` count=6 |
| 写 `min_fps` 时是否发命令 | 不发送 | 发送，日志 `[A0033] dsi_cmd: qcom,mdss-dsi-bigdc-adfr-min-fps-N-command` |
| 面板物理 TE（`test_te`） | 60 | 60（**不跟随**） |

即：**框架→驱动的 ADFR 通路打通了**，但 AE084 的 DDIC 不认 AD296/AC180 那套寄存器。

## 为什么 AE084 之前完全没有 ADFR

本机 DTBO 里同一块板子（TE gpio `0x56`、reset gpio `0xab`、panel-gpio1 `0x93`、
panel-gpio2 `0x36`、物理尺寸 `0x9d x 0x47` 全部相同）有两家面板：

- `AC180_P_3_A0020`：完整 ADFR（`oplus,adfr-config = <0xe51>`、三家命令族、
  mapping table），命令用 `FF 5A A5 2D` 页。
- `AE084_P_3_A0033`（dvt02/dvt03）：**零 ADFR 属性**，初始化命令用
  `F0 55 AA 52` 页族（另见 `FF AA 55 A5 80/81/82`），完全没有
  `qcom,mdss-dsi-*-adfr-min-fps-*` 属性。

AD296（1+15）与 AC180 的 min-fps 命令族逐字节一致，属于同一 DDIC 家族。

## min-fps 寄存器值的通用规律（已解出）

寄存器值 = `节点基频 / 目标fps − 1`（以该基频的帧周期为保持单位）：

- 120 基频节点：`00 01 03 05 0b 77` → 120/60/30/20/10/1
- 60 基频节点：`01 02 03 05 0b 77` → 60/40/30/20/10/1
- 90 基频节点（AD296）：`85` 寄存器，`00 01 02 05 08 59` → 90/45/30/15/10/1

所以**数值是通用的**，面板私有的只有「写在哪个页、哪个寄存器」。

## 注入内容

`tools/inject_rmx5200_adfr.py` 对 DTBO 的 0–3 号 entry 中
`qcom,mdss_dsi_panel_AE084_P_3_A0033_dsc_cmd_dvt02` 节点做两件事：

1. 面板级插入：`qsync-min-refresh-rate`、`qsync-enable`、
   `oplus,adfr-test-te-gpio = <0xffffffff 0x55 0x0>`、`oplus,adfr-config = <0xe51>`。
2. `timing@wqhd_sdc_120` 与 `timing@wqhd_sdc_60` 各插入 37 行：
   三家命令族（bigdc reg `0x84`、hpwm/adfr reg `0x83`）的 min-fps 0..5
   command / command-state，加 `oplus,adfr-min-fps-mapping-table`。

`0x83`/`0x84` 页面为 `FF 5A A5 2D`；命令字节与 AC180 模板逐字节一致。

## 已知缺口

`test_te` 在 `min_fps` 被写成 60/30/10/1 后始终为 60，即面板物理刷新率没有变化。
驱动把命令发出去了，但 AE084 的 DDIC 忽略 `FF 5A A5 2D` / `0x83`/`0x84`。
下一步需要 AE084 自己的低刷寄存器；候选是它自己的 `F0 55 AA 52 08 00` 页 `0x68`
寄存器族（`00`=60 / `01`=90 / `10`=120 / `30`=144，来自原生
`qcom,mdss-dsi-fps-switch-*`），或 `a9` timing 表。

## 2026-09-26 追加：test-TE 修正与 AE084 自己的档位选择器

### test-TE 不可用于 AE084

第一版照抄 AC180 的 `oplus,adfr-test-te-gpio = <0xffffffff 0x55 0x0>`，驱动日志
报 `test te gpio is invalid, use current timing refresh rate`，即 `test_te` 只是
回显当前档位、不是真实测量。改成 AE084 自己的 TE 脚 `<0xffffffff 0x56 0x0>`
后**依旧报 invalid**，说明 AE084 这条 ADFR test-TE 通道不通，`test_te` 无法
用来判定面板物理刷新率。后续必须换别的判据（肉眼/功耗/DSI 时序）。

### 命令确实按表发出

`min_fps` 扫描时驱动日志逐档对应正确：

| min_fps | 发出的命令 | 表索引 |
|---|---|---|
| 120 | `bigdc-adfr-min-fps-0-command` | 0（mapping[0]=120） |
| 30  | `bigdc-adfr-min-fps-2-command` | 2（mapping[2]=30） |
| 10  | `bigdc-adfr-min-fps-4-command` | 4（mapping[4]=10） |
| 1   | `bigdc-adfr-min-fps-5-command` | 5（mapping[5]=1） |

所以"框架→驱动→DSI 发送"这条链已经完整可用，缺的只是 AE084 认得的那条命令。

### AE084 自己的档位选择器

把四个 WQHD timing 的 on-command 拆包逐条对比，除 gamma LUT（E1/E2/E3）与
`A9` timing 表外，唯一随档位单调变化的字段是：

```text
39 00 00 00 01 00 8b a9 01 00 2f 00 00 <VAL>
                                         ^^^
  144Hz -> 0x00
  120Hz -> 0x01
   90Hz -> 0x02
   60Hz -> 0x03
```

即 AE084 DDIC 内部有一张档位表，`VAL` 是反向索引（值越大越慢）。
`VAL > 3` 是否还有更低档位，是下一步最值得试的点。

### 外来的 FF 5A A5 2D 页会打坏画面

把 min_fps 强制压到 1/10/30 时，面板出现"偏绿的纯白"。说明
`FF 5A A5 2D` 页写确实到达了 DDIC，但落到了 AE084 的错误寄存器。
**这是当前 DTBO 里的一个隐患**：只要框架开始请求低档，就会重现。

### ColorOS 自己的 LTPO 策略未启动

开启 ADFR 后 `dumpsys SurfaceFlinger` 仍是
`displayManagerPolicy primaryRanges=[120,120]`、`idleScreenConfig=nullptr`，
说明 ColorOS 的空闲降频策略没有因为 ADFR 可用而启动。

## 2026-09-26 物理低刷（目标 A）的最终定位

### 面板侧：AE084 没有「主机可写」的降帧寄存器

在 `runtime/skip_kernel_modules` 纯测试环境下，用 `dri/0/DSI-1/tx_cmd` 逐条实打
（写进去都返回 `rc=0`，且已证明能到达 DDIC —— 越界写 `a9` 索引会把画面打成偏色，
切档即复原）：

| 候选 | 写值 | 结果 |
|---|---|---|
| `0x68`（原生档位寄存器） | `10`(120Hz) | 无可见变化 |
| `b7` 帧周期表 `0x0c-0x0f` | `2500`(~4.8Hz) | 无可见变化 |
| `b7` 帧周期表 `0x0c-0x0f` | `12000`(~1Hz) | 无可见变化 |
| `b7 0x10-0x1f`（20/10/8/6Hz 那 8 项） | `12000` | 无可见变化 |
| `0x09bd`（报文里被写 `05`/`04` 两次的可疑寄存器） | `05`/`0b`/`77`/`00` | 无可见变化 |
| `0x09be` / `0x09bc` | `77` | 无可见变化 |
| AOD 命令组（`aod-low/high`、`nolp`、`lp1`） | 原值 | 仅亮度 + DCS `0x38`/`0x39` |

结论：`b7` 那张 20/10/8/6/4.8Hz 的帧周期表**不是给主机调的**，是 DDIC 自主
使用的；AE084 的 DSI 命令集里没有任何帧保持寄存器。

### 机制侧：低刷是 DDIC 自主行为

`nolp` 里的 DCS `0x38` = Enter Idle Mode。Idle Mode 下 DDIC 自己接管时序、
按 `b7` 表降帧。即物理低刷的触发条件是「**系统停止送新帧**」，而不是某个寄存器。

### 系统侧：内核没有暴露 VRR 能力，框架不会进 idle

```text
/sys/kernel/debug/dri/0/DSI-1/vrr_range   →  Min: 0  Max: 0
SurfaceFlinger activeMode                 →  vrrConfig=N/A
dumpsys display mDisplayModeSpecs         →  idleScreenRefreshRateConfig = null
DMABUF connector (card0-DSI-1)            →  no vrr attribute at all
```

修好 `post-fs-data.sh` 的 `exit 0` 之后，`vendor.display.enable_qsync_idle` /
`enable_allow_idle_fallback` 已置 1，框架侧窗口确实打开了
（`appRequest` 从 `[120,120]` 变成 `[0,120]`，`mSupportedRefreshRates`
报出 `[144…28.8]`），但**内核 DRM connector 的 VRR 范围仍是 0/0**，SurfaceFlinger
拿不到 `VrrConfig`，因此 `idleScreenRefreshRateConfig` 始终为 `null`。

### 下一步

让 msm_drm / 面板驱动把真实的 VRR 范围暴露成 DRM connector 的 vrr_config
（用户态可见）。这条只能在**内核侧**做，是 KO 的典型用武之地：
在 connector 初始化后补上 vrr range / vrr_config，SurfaceFlinger 才会生成
idle 配置，进而空闲停送帧，DDIC 按 `b7` 自主降到 4.8~20Hz。
