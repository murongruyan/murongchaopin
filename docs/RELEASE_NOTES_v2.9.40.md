# 慕容显示增强 v2.9.40

本版修复用户反馈的两个问题：刷新率设置报“刷新率桥接失败”，以及刷新率切换时的卡顿。
同时统一了守护进程版本号并修正构建脚本的源码指纹。

## 修复内容

### 一、刷新率设置报“刷新率桥接失败”（用户反馈）

部分机型（PLK110）的设置页读到的分辨率，与面板实际可用的分辨率不是同一套值。
面板的模式表里只有 1272x2772 和 1080x2354 两组几何，而设置页报上来的是系统记录的
偏好宽高。旧版守护进程要求“宽、高、刷新率”三项在模式表里精确命中，于是每一次点选
都被判为不支持，弹窗只显示“刷新率桥接失败”。

更麻烦的是这个分支原本不写任何日志，所以反馈包里看不到一条记录 —— 这正是该问题
难以定位的原因。

本版把两种失败区分开：

- 模式表里**根本不存在**这个几何 → 判定为客户端持有过期信息，改用当前实际驱动的几何；
- 模式表里**存在**该几何但不支持所选刷新率 → 仍然如实拒绝，不会把不支持的档位放过去。

回退到实际几何时会写一条明确日志，以后再出现同类问题可以直接从日志看出。

### 二、刷新率切换卡顿（用户反馈：页面停顿后手势卡、视频返回卡一下）

刷新率阶梯切换的每一步，都会先重发一次“当前已经生效的档位”，再去请求目标档位。
这个设计的本意是防止过期的策略让新请求变成空操作。但当那个“当前档位”正是守护进程
自己刚刚下发并已确认生效的档位时，这次重发没有任何作用，却让一次切换的
SurfaceFlinger 事务凭空翻倍。

每一次这样的重发都要 fork 一个 shell 进程并重新占用 SurfaceFlinger 锁，锁定期间
合成被挡住 —— 这就是滑动返回、视频退出时那一下卡顿的来源。

本版只在确认该档位确实是自身上一次请求留下的策略时才跳过重发，并设 4 秒信任窗口：
外部（系统或第三方应用）改动过策略时，仍会正常对齐，不会因为省这一步而让请求失效。

顺带减少了一类重复的 OTI 暂停下发：阶梯每一步、每次抬手都会重新下发 OTI 暂停，
这些调用会和 500ms 心跳落在同一个窗口，导致刚确认过的状态被立刻重发。本版只跳过
这种毫秒级重复。**500ms 心跳节奏完全没有改动** —— 该节奏是 v2.9.38 修复周期性
黑闪的一部分，不属于可优化项。

### 三、版本号与构建指纹

- 内置守护进程上报的版本一直是 `2.9.38`，与模块的 `2.9.39` 对不上，会让后续排查
  误判版本，本版统一为 `2.9.40`；
- Windows 下 `core.autocrlf` 会把源文件转成 CRLF，构建脚本原来直接对该文件取哈希，
  记录下的指纹与 Linux 构建机（LF）永远不一致，会让发布流水线的产物指纹校验失败。
  现在按 LF 计算，与本地产物和 CI 一致。

## 真机验证

- 系统：`RMX5200` / ColorOS 17 / 内核 `6.12.69`。
- 几何不匹配场景：`1272x2772 165Hz`、`1272x2772 120Hz` 修复前返回 `ERR mode`，
  修复后正常返回；真不支持的 `1440x3136 170Hz` 仍返回 `ERR mode`。
- 一次 `120Hz -> 165Hz` 切换的 SurfaceFlinger 事务数由 6 降到 4，其中冗余的
  “对齐过期策略”由每步一次（共 3 次）降到仅首次真实漂移（1 次）；切换全程约 3 秒。
- 验证结束后设备已恢复到 `1440x3136 120Hz`，未出现黑闪、dpi 跳动或分辨率漂移。

## 安装说明

在 KernelSU、Magisk 或 APatch 中刷入 Release 附带的
`Murong.Display.Enhancement-v2.9.40.zip`，然后完整重启设备。

付费组件（ADFR 锁、视频插帧）需要单独下载付费包，本版付费包为 `1.1.22`。
